# 小区物业管理系统 — 项目记录

> 记录项目开发过程中遇到的问题、解决方案及经验总结。

---

## 一、环境搭建阶段

### 问题 1：Spring Boot 3.x 与 Java 版本不兼容

**现象：** 项目启动时报错 `Unsupported class file major version`

**原因：** Spring Boot 3.x 要求最低 Java 17，而本地默认 JDK 版本是 Java 8 或 11。

**解决方案：**
- 安装 JDK 17，并在 IDE 中配置项目 SDK 为 17
- 在 `pom.xml` 中明确指定 `<java.version>17</java.version>`
- Maven 编译时也指定 JDK 17 路径

**经验：** 升级框架前一定要先确认 JDK 版本要求。

---

### 问题 2：MySQL 连接时区错误

**现象：** 启动时报错 `The server time zone value 'ÖÐ¹ú±ê×¼Ê±¼ä' is unrecognized`

**原因：** MySQL 数据库的时区设置与 JDBC 连接参数不一致。

**解决方案：** 在 `application.yml` 的数据库连接 URL 中添加 `serverTimezone=Asia/Shanghai`：
```yaml
url: jdbc:mysql://localhost:3306/property_management?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai
```

**经验：** JDBC 连接 MySQL 8.0 时，时区参数是必填项。

---

### 问题 3：Druid 连接池依赖找不到

**现象：** Maven 报错 `Could not resolve dependency: com.alibaba:druid-spring-boot-starter`

**原因：** Spring Boot 3.x 需要使用 `druid-spring-boot-3-starter`，而不是旧版的 `druid-spring-boot-starter`。

**解决方案：**
```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid-spring-boot-3-starter</artifactId>
    <version>1.2.21</version>
</dependency>
```

**经验：** Spring Boot 大版本升级时，第三方 Starter 通常也需要对应升级。

## 二、后端开发阶段

### 问题 4：MyBatis 驼峰命名映射不生效

**现象：** 数据库字段 `id_card` 查出来后，Java 对象的 `idCard` 属性始终为 null。

**原因：** MyBatis 默认不会自动将下划线命名转换为驼峰命名。

**解决方案：** 在 `application.yml` 中开启驼峰映射：
```yaml
mybatis:
  configuration:
    map-underscore-to-camel-case: true
```

同时在 XML 映射文件中使用 `resultMap` 显式指定映射关系：
```xml
<resultMap id="ownerResultMap" type="Owner">
    <id property="id" column="id"/>
    <result property="idCard" column="id_card"/>
    <result property="moveInDate" column="move_in_date"/>
</resultMap>
```

**经验：** 两种方式可以配合使用，`resultMap` 优先级更高。

---

### 问题 5：Spring Security 拦截了所有请求导致前端无法访问

**现象：** 前端所有 API 请求都返回 401，包括登录接口。

**原因：** Spring Boot 3.x 中 Spring Security 的配置方式发生了变化，旧版的 `WebSecurityConfigurerAdapter` 已废弃。

**解决方案：** 使用新的 `SecurityFilterChain` Bean 配置方式：
```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()  // 放行登录接口
            .anyRequest().authenticated()
        )
        .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
```

**经验：** Spring Boot 3.x 的 Security 配置 API 变化很大，需要查阅最新文档。

---

### 问题 6：JWT Token 验证失败，前端收到 401

**现象：** 登录成功后获取到 Token，但后续请求仍然返回 401。

**原因：**
1. `JwtAuthenticationFilter` 没有正确从 Header 中提取 Token
2. Token 的 Secret Key 与生成时使用的不一致

**解决方案：**
- 确保 Filter 从 `Authorization: Bearer <token>` 格式中正确提取 Token
- 确保 `JwtUtil` 中的 Secret Key 与 `application.yml` 中配置的一致
- 在 Filter 中将解析出的用户信息设置到 `SecurityContextHolder` 中

**经验：** JWT 调试时，可以先用在线工具（如 jwt.io）验证 Token 的 payload 是否正确。

---

### 问题 7：MyBatis XML 中的动态 SQL 条件拼接错误

**现象：** 查询时如果某个条件为空，SQL 语法报错。

**原因：** `<where>` 标签内的 `<if>` 条件判断不严谨，空字符串没有排除。

**解决方案：**
```xml
<where>
    <if test="name != null and name != ''">
        AND name LIKE CONCAT('%', #{name}, '%')
    </if>
    <if test="phone != null and phone != ''">
        AND phone LIKE CONCAT('%', #{phone}, '%')
    </if>
</where>
```

**经验：** MyBatis 动态 SQL 中，`<if>` 条件要同时判断 `null` 和空字符串。

---

### 问题 8：删除业主时外键约束报错

**现象：** 删除有关联数据的业主时，MySQL 报错 `Cannot delete or update a parent row: a foreign key constraint fails`

**原因：** 外键约束默认不允许删除有关联数据的父记录。

**解决方案：** 在建表时设置合适的外键约束策略：
- 费用、投诉、报修表使用 `ON DELETE CASCADE`（级联删除）
- 房屋、停车位表使用 `ON DELETE SET NULL`（关联置空）

```sql
FOREIGN KEY (`owner_id`) REFERENCES `owner`(`id`) ON DELETE CASCADE
FOREIGN KEY (`owner_id`) REFERENCES `owner`(`id`) ON DELETE SET NULL
```

**经验：** 外键策略要根据业务场景选择，不能一刀切。

## 三、前端开发阶段

### 问题 9：Vite 开发服务器代理配置不生效

**现象：** 前端请求 `/api/owner/page` 返回 404，没有代理到后端。

**原因：** `vite.config.ts` 中的代理配置路径不正确。

**解决方案：**
```typescript
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      }
    }
  }
})
```

**经验：** Vite 代理只在开发模式下生效，生产环境需要用 Nginx 反向代理。

---

### 问题 10：React 组件中 useEffect 导致无限循环请求

**现象：** 页面打开后，网络请求不断发送，浏览器卡顿。

**原因：** `useEffect` 的依赖数组中包含了每次渲染都会重新创建的对象或函数。

**解决方案：** 使用 `useCallback` 包裹请求函数，并确保依赖数组中的值是稳定的：
```typescript
const fetchData = useCallback(async () => {
  setLoading(true)
  try {
    const { data: res } = await ownerApi.page({ name: searchName, phone: searchPhone, pageNum, pageSize: 10 })
    setData(res.list)
    setTotal(res.total)
  } catch { /* ignore */ }
  finally { setLoading(false) }
}, [searchName, searchPhone, pageNum])  // 只有这些值变化时才重新创建

useEffect(() => { fetchData() }, [fetchData])
```

**经验：** React 19 的 StrictMode 会双重调用 useEffect，开发时要注意依赖管理。

---

### 问题 11：TypeScript 类型报错 — Axios 响应类型

**现象：** `const { data: res } = await ownerApi.page(...)` 中 `res` 的类型推断不正确。

**原因：** Axios 的响应类型嵌套了两层 `data`（AxiosResponse.data），类型推断混乱。

**解决方案：** 在 `api.ts` 中封装通用的请求函数，统一处理类型：
```typescript
async function request<T>(config: AxiosRequestConfig): Promise<T> {
  const { data } = await axiosInstance.request<T>(config)
  return data
}
```

**经验：** Axios 的 `response.data` 是实际响应体，封装一层可以避免类型混乱。

---

### 问题 12：Tailwind CSS 4 与 Vite 8 的兼容性问题

**现象：** Tailwind CSS 的样式没有生效，页面显示为无样式状态。

**原因：** Tailwind CSS 4 改用了新的 Vite 插件方式，不再使用 PostCSS 插件。

**解决方案：** 使用 `@tailwindcss/vite` 插件：
```typescript
// vite.config.ts
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})
```

**经验：** Tailwind CSS 4 是一次重大升级，配置方式与 3.x 完全不同。

## 四、数据库设计阶段

### 问题 13：E-R 图设计时表关系混乱

**现象：** 初期设计时把房屋和业主设计成了多对多关系，增加了不必要的中间表。

**原因：** 对业务场景理解不够深入，实际中一套房屋在同一时间只属于一个业主。

**解决方案：** 改为一对多关系，在 `house` 表中添加 `owner_id` 外键：
```sql
`owner_id` INT DEFAULT NULL,
FOREIGN KEY (`owner_id`) REFERENCES `owner`(`id`) ON DELETE SET NULL
```

**经验：** 数据库设计前要先梳理清楚业务实体之间的实际关系。

---

### 问题 14：缺少值班表的外键约束

**现象：** 删除员工时，该员工的值班记录变成了"孤儿数据"。

**原因：** `duty` 表的 `employee_id` 字段没有设置外键约束。

**解决方案：** 添加外键约束并设置级联删除：
```sql
FOREIGN KEY (`employee_id`) REFERENCES `employee`(`id`) ON DELETE CASCADE
```

**经验：** 所有关联字段都应该考虑是否需要外键约束。

## 五、部署与调试阶段

### 问题 15：前后端联调时 CORS 跨域被浏览器拦截

**现象：** 前端请求后端 API 时，浏览器控制台报 CORS 错误。

**原因：** 前端运行在 `localhost:3000`，后端运行在 `localhost:8080`，属于不同源。

**解决方案：**
- **开发阶段**：使用 Vite 的 `server.proxy` 代理（推荐）
- **后端兜底**：在 Spring Security 配置中添加 CORS 支持：
```java
http.cors(cors -> cors.configurationSource(corsConfigurationSource()))
```

**经验：** 开发时用代理，生产时用 Nginx，CORS 配置只是兜底方案。

---

### 问题 16：BCrypt 密码验证总是失败

**现象：** 登录时密码明明正确，但 `passwordEncoder.matches()` 返回 false。

**原因：** 数据库中存储的 BCrypt 哈希值与当前输入的密码不匹配，可能是手动插入测试数据时用了错误的哈希值。

**解决方案：** 使用 Java 代码生成正确的 BCrypt 哈希值：
```java
PasswordEncoder encoder = new BCryptPasswordEncoder();
String hash = encoder.encode("admin123");
System.out.println(hash);  // 输出正确的哈希值，替换到 SQL 中
```

**经验：** BCrypt 每次加密结果都不同（因为包含随机盐），但验证时能正确匹配。

## 六、经验总结

### 技术选型方面
1. Spring Boot 3.x + MyBatis 是目前最主流的 Java Web 技术栈，生态成熟
2. React 19 + TypeScript + Tailwind CSS 4 是前端的最佳实践组合
3. JWT 无状态认证适合前后端分离架构

### 开发流程方面
1. 先设计数据库，再写后端 API，最后做前端页面，效率最高
2. 每个模块的 CRUD 代码结构高度相似，可以形成模板后批量生成
3. 遇到问题先查官方文档，再查 Stack Overflow，最后问 AI

### 代码质量方面
1. 统一的 API 响应格式（`{ code, msg, data }`）让前后端对接更顺畅
2. MyBatis XML 映射比注解方式更适合复杂 SQL
3. 前端组件化（DataTable、FormModal、ConfirmDialog）提高了代码复用率

### 遗留问题与改进方向
1. ~~缺少全局异常处理器~~ → 已实现 `GlobalExceptionHandler`（`@RestControllerAdvice`）
2. ~~没有实现角色权限控制~~ → 已实现 RBAC（admin 可增删改，user 仅查看）
3. 缺少单元测试和接口测试
4. 没有 Docker 容器化部署方案
5. Dashboard 缺少图表统计功能
