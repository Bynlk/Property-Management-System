**核心关联关系：**

- `owner` ↔ `fee`：一个业主有多条欠费记录（一对多）
- `owner` ↔ `parking`：一个业主有停车位（一对一/一对多）
- `owner` ↔ `complaint`：一个业主有多条投诉（一对多）
- `owner` ↔ `repair`：一个业主有多条报修（一对多）
- `employee` ↔ `duty`：一个员工有多条值班记录（一对多）

**外键约束策略：**
- 删除业主时，关联的费用、投诉、报修级联删除（`CASCADE`）
- 删除业主时，房屋、停车位的关联置空（`SET NULL`）

### 第6页：技术亮点 — 万能关联查询（2分钟）

> 这是本系统的核心技术亮点

**场景：** 业主详情页需要在一个界面中展示该业主的所有关联信息

**传统做法的问题：**
- 需要分别查询 6 张表，发送 6 次 SQL 请求
- 前端需要多次异步请求，页面加载慢
- 数据一致性难以保证

**本系统的做法：**

在 [`OwnerMapper.xml`](src/main/resources/mapper/OwnerMapper.xml) 中使用 MyBatis 的多表关联查询：

```sql
SELECT 
    o.*,
    h.id AS house_id, h.building, h.unit, h.room_number, h.area, h.house_type, h.status AS house_status,
    f.id AS fee_id, f.fee_type, f.amount, f.should_pay_date, f.status AS fee_status,
    c.id AS complaint_id, c.title, c.create_time, c.status AS complaint_status,
    r.id AS repair_id, r.device_name, r.fault_description, r.repair_person, r.status AS repair_status,
    p.id AS parking_id, p.spot_number, p.license_plate, p.status AS parking_status
FROM owner o
LEFT JOIN house h ON o.id = h.owner_id
LEFT JOIN fee f ON o.id = f.owner_id
LEFT JOIN complaint c ON o.id = c.owner_id
LEFT JOIN repair r ON o.id = r.owner_id
LEFT JOIN parking p ON o.id = p.owner_id
WHERE o.id = #{id}
```

**技术要点：**
- 使用 `LEFT JOIN` 确保即使某类关联数据为空，业主基本信息也能返回
- MyBatis 的 `resultMap` 处理复杂的结果集映射
- 一次查询获取所有关联数据，减少数据库交互次数

**前端展示：**
- 使用 Tab 页切换展示不同类型的信息
- 每个 Tab 内用小表格展示对应数据
- 整体用卡片布局，用户体验友好

## 二、项目亮点自述（2分钟讲稿）

各位老师好，我来介绍一下我这个小区物业管理系统的技术亮点。

这个系统采用前后端分离架构，后端用 Spring Boot + MyBatis，前端用 React + TypeScript + Tailwind CSS，数据库是 MySQL。

我觉得这个项目最大的技术亮点是**业主详情页的万能关联查询**。在实际的物业管理场景中，当我们点开一个业主的详情页时，需要同时看到他的房产信息、欠费记录、投诉记录、报修记录、停车位信息。传统的做法是分别查 6 张表，发 6 次 SQL 请求，前端再发 6 次异步请求去拿数据。这样做不仅慢，而且数据一致性也很难保证。

我的做法是在 MyBatis 的 XML 映射文件中，用 **LEFT JOIN** 把 6 张表关联起来，**一条 SQL 就把所有信息查出来**。这样做的好处是：第一，减少了数据库交互次数，查询效率更高；第二，数据在同一事务中获取，一致性有保障；第三个好处是前端只需要一次请求就能拿到完整数据，页面加载速度更快。

另外在前端 UI 设计上，我采用了 **Liquid Glass** 设计语言，用了毛玻璃效果、鼠标追踪光效、交错动画等技术，让整个系统的界面看起来比较现代化，不是那种传统的后台管理系统的"表格堆砌"的感觉。

总的来说，这个系统虽然功能不算特别复杂，但在数据关联查询和前端交互体验上做了一些有意义的探索。谢谢各位老师。

## 三、评委可能问的 5 个技术问题及回答要点

### Q1：你们为什么用 Spring Boot 而不是传统的 SSM 框架？

**回答要点：**
- Spring Boot 是 Spring MVC + Spring + MyBatis 的**整合升级版**，本质上还是 SSM 的技术栈
- Spring Boot 的优势在于**自动配置**和**约定优于配置**，大大减少了 XML 配置文件的数量
- 内嵌 Tomcat，不需要额外部署到外部容器，`mvn spring-boot:run` 一键启动
- 配合 Spring Boot Starter 依赖管理，版本兼容性更好
- 本质上是 SSM 的现代化实践，不是"不用 SSM"，而是"用更好的方式用 SSM"

### Q2：多表关联查询是怎么实现的？为什么用 LEFT JOIN 而不是 INNER JOIN？

**回答要点：**
- 在 [`OwnerMapper.xml`](src/main/resources/mapper/OwnerMapper.xml) 中使用 MyBatis 的 XML 映射文件编写 SQL
- 使用 `LEFT JOIN` 而不是 `INNER JOIN`，原因是：业主可能还没有投诉记录、报修记录或停车位
- 如果用 `INNER JOIN`，没有关联数据的业主就查不出来
- `LEFT JOIN` 保证了即使关联表没有数据，业主的基本信息也能返回，关联字段为 NULL
- MyBatis 的 `resultMap` 负责将复杂的多表结果集映射到 Java 对象中

### Q3：如果数据量大了怎么优化？

**回答要点：**
- **数据库层面**：
  - 为外键字段和常用查询字段添加索引（如 `owner_id`、`name`、`phone`）
  - 使用分页查询（`LIMIT`），避免一次性加载全部数据
  - 考虑读写分离，主库写、从库读
- **缓存层面**：
  - 引入 Redis 缓存热点数据（如业主基本信息、房屋信息）
  - 设置合理的缓存过期策略
- **应用层面**：
  - 万能关联查询可以改为按需查询，只查用户当前 Tab 需要的数据
  - 使用异步查询，并行获取不同类型的数据
- **架构层面**：
  - 数据量特别大时可以考虑分库分表
  - 使用 Elasticsearch 做全文搜索

### Q4：JWT 认证的流程是怎样的？Token 过期了怎么办？

**回答要点：**
- **登录流程**：用户提交用户名密码 → 后端验证 → 验证通过后用 [`JwtUtil`](src/main/java/com/property/security/JwtUtil.java) 生成 JWT Token 返回给前端
- **请求流程**：前端每次请求在 Header 中携带 `Authorization: Bearer <token>` → [`JwtAuthenticationFilter`](src/main/java/com/property/security/JwtAuthenticationFilter.java) 拦截请求 → 解析并验证 Token → 验证通过则放行
- **Token 过期**：配置的过期时间是 24 小时（86400000ms），过期后前端收到 401 响应 → 跳转到登录页重新登录
- **密码安全**：使用 BCrypt 算法加密存储密码，数据库中不存明文
- **无状态设计**：服务端不存储 Session，适合分布式部署

### Q5：前后端分离是怎么做的？跨域问题怎么解决的？

**回答要点：**
- **前后端分离**：前端是独立的 React 项目（Vite 构建），后端是 Spring Boot 提供 RESTful API
- **开发阶段**：Vite 配置了代理（`proxy`），将 `/api` 请求转发到后端 `localhost:8080`，避免跨域
- **生产阶段**：前端打包成静态文件，用 Nginx 部署，Nginx 反向代理 `/api` 到后端
- **跨域处理**：在 [`SecurityConfig`](src/main/java/com/property/security/SecurityConfig.java) 中配置了 CORS，允许所有来源访问
- **接口规范**：统一的 JSON 响应格式，分页查询返回 `{ list, total, pageNum, pageSize }`，增删改返回 `{ code, msg }`
