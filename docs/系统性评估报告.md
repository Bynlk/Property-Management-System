## 二、架构设计（9.5/10）

### 2.1 分层架构

项目采用经典的四层架构：**Controller → Service → Mapper → Entity**，辅以 `common` 包提供跨切面关注点，`dto` 包处理请求/响应对象。

```
src/main/java/com/property/
├── common/          # 10 个通用类：BaseMapper, BaseService, BaseCrudController, Result, PageHelper...
├── controller/      # 10 个 Controller（8 业务 + Auth + Dashboard）
├── dto/             # 17 个 DTO（8×2 Create/Update + LoginRequest）
├── entity/          # 10 个实体（8 业务 + User + StatusChangeLog）
├── enums/           # 10 个文件（8 个枚举 + CodeEnum 接口 + CodeEnumTypeHandler）
├── mapper/          # 10 个 MyBatis Mapper 接口
├── security/        # 4 个安全组件（JWT + Filter + Config + RateLimit）
├── service/         # 9 个 Service 接口 + 9 个实现
└── config/          # OpenApiConfig
```

**量化数据：**
- Java 源文件：~91 个（common 10 + controller 10 + dto 17 + entity 10 + enums 10 + mapper 10 + security 4 + service 18 + config 1 + 启动类 1）
- Controller → Service 调用率：100%（零 Controller 直接访问 Mapper）
- 构造器注入率：100%（全部使用 `@RequiredArgsConstructor`，零 `@Autowired` 字段注入）

### 2.2 泛型 CRUD 框架

项目的核心架构亮点是三层泛型基类体系：

| 基类 | 泛型参数 | 职责 | 被继承次数 |
|:---|:---|:---|:---:|
| `BaseMapper<T>` | 实体类型 | 定义 5 个标准 CRUD 方法 | 8/10 Mapper（UserMapper 和 StatusChangeLogMapper 因自定义方法未继承） |
| `BaseService<T, M>` | 实体 + Mapper | 提供 getById/add/update/delete/getAll | 8/9 Service |
| `BaseCrudController<T, C, U, S>` | 实体 + CreateDTO + UpdateDTO + Service | 提供 5 个标准 REST 端点 | 8/10 Controller |

**量化收益：** 8 个 Controller × 5 个端点 = **40 个 REST 端点**由 BaseCrudController 自动生成。每个子 Controller 仅需实现 ~8 个模板方法（约 30-40 行），相比手写每个端点节省约 **80%** 代码量。

### 2.3 前端架构

前端同样实现了高度抽象：

- **`crud<T>(base)` API 工厂**：一行代码定义一个资源的完整 CRUD API
- **`CrudPage<T>` 组件**：配置驱动，8 个业务页面各仅需 ~40 行配置代码
- **`useCrudPage` Hook**：管理完整 CRUD 生命周期（分页、搜索、提交、删除）
- **`useCrudSearch` Hook**：组合 `useDebounce`，区分文本字段（防抖）和 select 字段（即时触发）

**前端源文件统计：**
- 组件：11 个（Layout, DataTable, FormModal, ConfirmDialog, CrudPage, FilterSelect, Toast, ErrorBoundary, PageHeader, ActionColumn, FlowParticles）
- 页面：10 个（Login + Dashboard + 8 业务）
- Hook：3 个（useDebounce, useCrudPage, useCrudSearch）
- 工具：3 个（apiError, formData, dropdownArrow）

### 2.4 架构优势总结

1. **关注点分离严格**：Controller 仅负责 HTTP 协议转换，Service 包含业务逻辑，Mapper 纯数据访问
2. **模板方法模式**：BaseCrudController 的抽象方法强制子类实现关键逻辑，同时复用通用流程
3. **泛型类型安全**：从 Mapper 到 Service 到 Controller 全链路泛型传递，编译期保证类型正确
4. **配置驱动 UI**：CrudPage 将 8 个业务页面统一为纯配置对象，消除前端重复

### 2.5 架构待改进项

| 问题 | 影响 | 建议 |
|:---|:---|:---|
| Entity 上仍保留 Jakarta Validation 注解 | 与 DTO 层验证重复 | 仅在 DTO 上保留验证，Entity 仅做 ORM 映射 |
| UpdateRequest DTO 中的 `id` 字段未使用 | 死代码 | 从 UpdateRequest 中移除 `id` 字段 |
| 无 Response DTO | Entity 直接暴露为 API 响应 | 为敏感实体（Owner, User）创建 Response DTO |
| 前端 `formDataToPayload` 未被引用 | 死代码 | 删除或集成到 useCrudPage |

### 3.4 防暴力破解

`LoginAttemptService` 实现 IP+用户名 维度的速率限制：
- 5 次失败 → 15 分钟锁定
- 自动解锁（ConcurrentHashMap + 过期清理）
- 支持 X-Forwarded-For / X-Real-IP 代理头

### 3.5 数据保护

- **身份证脱敏**：`IdCardMaskSerializer` 将 `110101199001011234` 显示为 `1101**********1234`
- **密码不序列化**：`User.password` 标注 `@JsonIgnore`
- **SQL 注入防护**：MyBatis 参数化查询（`#{}` 占位符）
- **错误信息脱敏**：GlobalExceptionHandler 捕获 SQL 异常后返回通用消息

### 3.6 安全待改进项

| 问题 | 风险等级 | 建议 |
|:---|:---:|:---|
| Token 存储在 localStorage | 中 | 考虑 httpOnly Cookie（需服务端配合） |
| 24 小时 Token 过期时间较长 | 低 | 缩短至 2 小时 + Refresh Token 机制 |
| 速率限制仅内存存储 | 低 | 多实例部署需改用 Redis |
| CORS 允许 `unsafe-inline` | 低 | 生产环境收紧 CSP |

## 五、状态机设计（9.5/10）

### 5.1 状态机定义

项目实现了 **5 个正式状态机**，使用不可变 `Map<E, Set<E>>` 转移表：

| 实体 | 状态数 | 转移路径 | 特性 |
|:---|:---:|:---|:---|
| 投诉 | 3 | 待处理 → 处理中 → 已处理 | 线性、终态不可逆 |
| 报修 | 3 | 待维修 → 维修中 → 已完成 | 线性、终态不可逆 |
| 费用 | 2 | 未缴 → 已缴 | 单向、不可逆 |
| 房屋 | 3 | 空置 ↔ 装修中 ↔ 已入住 ↔ 空置 | 双向（已入住↛装修中） |
| 停车位 | 2 | 空闲 ↔ 使用中 | 完全双向 |

### 5.2 状态机实现质量

```java
// 核心验证方法 — 泛型设计，适用于任意枚举类型
private static <E extends Enum<E>> void validateTransition(
    E current, E next, Map<E, Set<E>> transitions, String entityName) {
    if (current.equals(next)) return;  // 允许同状态更新其他字段
    Set<E> allowedTargets = transitions.get(current);
    if (allowedTargets == null || !allowedTargets.contains(next)) {
        throw new BusinessException(entityName + "不允许从「" + current + "」转换为「" + next + "」");
    }
}
```

**设计亮点：**
- 转移表使用 `Map.of()` 创建，运行时不可修改
- 同状态更新显式允许（更新其他字段不触发状态校验）
- 每个实体提供枚举类型和字符串类型双重重载（向后兼容）
- 空值检查 + 描述性错误消息

### 5.3 状态变更副作用

| 实体 | 审计日志 | 自动时间戳 |
|:---|:---:|:---:|
| 投诉 | ✅ status_change_log | ✅ resolved_at（变为"已处理"时） |
| 报修 | ✅ status_change_log | ✅ completed_at（变为"已完成"时） |
| 费用 | ❌ | ✅ paid_date（变为"已缴"时） |
| 房屋 | ❌ | ❌ |
| 停车位 | ❌ | ❌ |

### 5.4 状态机测试

`StatusValidatorTest` 包含 **28 个测试方法**，覆盖：
- 所有 5 个状态机的合法转移

## 六、数据库设计（9.0/10）

### 6.1 Schema 概览

10 张表，全部使用 InnoDB + utf8mb4：

| 表 | 列数 | 索引 | 外键 | UNIQUE | CHECK |
|:---|:---:|:---:|:---:|:---:|:---:|
| employee | 8 | 1 | 0 | phone | - |
| owner | 8 | 1 | 0 | phone, id_card | - |
| house | 10 | 3 | 1 | (building,unit,room) | area>0 |
| fee | 10 | 4 | 2 | - | amount>0 |
| parking | 7 | 3 | 1 | spot_number | - |
| complaint | 8 | 2 | 1 | - | - |
| repair | 9 | 2 | 2 | - | - |
| duty | 6 | 2 | 1 | (emp,date,shift) | - |
| sys_user | 8 | 0 | 0 | username | - |
| status_change_log | 7 | 2 | 0 | - | - |
| **合计** | **81** | **21** | **8** | **7** | **2** |

### 6.2 外键策略

| 关系 | 策略 | 设计意图 |
|:---|:---|:---|
| house → owner | SET NULL | 房屋可无主 |
| fee → owner | RESTRICT | 费用必须属于业主 |
| fee → house | SET NULL | 费用可不关联房屋 |
| parking → owner | SET NULL | 车位可无主 |
| complaint → owner | RESTRICT | 投诉必须属于业主 |
| repair → owner | RESTRICT | 报修必须属于业主 |
| repair → employee | SET NULL | 维修人员可为空 |
| duty → employee | CASCADE | 员工删除时级联删除值班 |

### 6.3 索引设计

**精心设计的复合索引：**
- `idx_fee_owner_status(owner_id, status)` — 优化"某业主未缴费用"高频查询
- `uk_duty(employee_id, duty_date, shift)` — 防止员工同日重复排班
- `idx_scl_entity(entity_type, entity_id)` — 审计日志按实体查询

### 6.4 数据库待改进项

| 问题 | 影响 | 建议 |
|:---|:---|:---|
| sys_user 无 role 索引 | 大量用户时按角色查询慢 | 添加 `idx_user_role` |
| complaint.resolved_at 无索引 | 时间范围报表查询慢 | 按需添加 |
| status_change_log.entity_type 用 VARCHAR | 类型不安全 | 改用 ENUM 或 CHECK 约束 |

## 十二、结论与建议

### 12.1 项目优势（可写入论文亮点）

1. **三层泛型 CRUD 框架**：BaseMapper → BaseService → BaseCrudController 的模板方法模式，实现 8 个业务模块的代码复用，消除约 80% 的重复代码
2. **配置驱动前端架构**：CrudPage + useCrudPage + crud<T>() 的三层抽象，将每个业务页面从 ~300 行缩减到 ~40 行配置
3. **形式化状态机**：5 个不可变转移表 + 泛型验证方法，确保状态转换的正确性和可追溯性
4. **纵深防御安全体系**：JWT + tokenVersion + RBAC + 速率限制 + 安全头 + 身份证脱敏 + 错误脱敏
5. **完整工程化链路**：Flyway 迁移 + Docker 容器化 + CI/CD 流水线 + Swagger 文档 + Actuator 监控

### 12.2 论文可讨论的改进方向

1. **数据级权限隔离（ABAC）**：当前 RBAC 仅控制操作权限，USER 角色可查看所有业主数据。可通过 `owner_id` 关联实现行级过滤
2. **Refresh Token 机制**：短生命周期 Access Token + 长生命周期 Refresh Token，平衡安全性与用户体验
3. **分布式速率限制**：将 LoginAttemptService 从 ConcurrentHashMap 迁移到 Redis，支持多实例部署
4. **E2E 测试**：引入 Playwright/Cypress 进行端到端测试，覆盖完整用户流程
5. **GraphQL 替代 REST**：对于复杂的关联查询场景，GraphQL 可减少 over-fetching

### 12.3 综合评价

本项目作为期末大作业，在架构设计、安全实现、工程化实践等方面均达到较高水准。泛型 CRUD 框架和配置驱动前端的设计体现了对 DRY 原则和关注点分离的深入理解。5 个形式化状态机、完整的 RBAC 安全体系、Docker 容器化和 CI/CD 流水线等实践已接近生产级项目水平。测试覆盖从修复前的 4/10 提升至 9.0/10，后端 233 个测试和前端 64 个测试（合计 297 个）为核心业务逻辑提供了可靠的回归保障。

主要提升空间在于：启用 TypeScript strict 模式、引入 Java 端静态分析工具、以及实现 Refresh Token 机制。
